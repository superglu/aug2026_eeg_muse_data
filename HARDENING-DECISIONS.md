## eo_ec_pipeline/classify.py:111 — Cross-branch accuracy compares 8 features (upsampled) against 4 (raw/denoised)  _(lens: correctness, round 1)_

The mechanical claim is accurate and unambiguous from the code: classify.py:106-111 pivots on whatever channels appear in that branch's rows and drops only block_idx/epoch_idx/condition, so X has one column per channel present. branches.py:132 passes POSTERIOR_TARGETS to reconstruct_fif and branches.py:138 prints 'upsampled -> ... (all 8ch model output)', and readme.MD:110-111 reports EC-EO dB for O1/O2/Oz/Pz in the upsampled branch — so the upsampled feature rows carry 8 channels while raw/denoised carry 4, and the per-branch mean_acc in readme.MD:115-117 is an 8-feature model compared against 4-feature models, with nothing in classify()'s output row (branch/mean_acc/std_acc/n_epochs) disclosing the difference. With ~30 epochs per fold and default-C LogisticRegression, doubling the feature count is not neutral. What blocks 'confirmed' is that the fix is a design decision, not a mechanical correction. Restricting to REAL_CHANNELS (the latent_tsne.py:13-17 choice) is one defensible reading, but the opposite reading is at least as defensible for this metric specifically: the extra posterior channels ARE the deliverable of the upsample branch, and README metric 6 frames accuracy as 'downstream task utility — the metric that actually matters for does the FM preserve brain state' (readme.MD:95), under a ranking criterion of 'accuracy preserved or increased vs. raw' (readme.MD:142) that a channel-adding branch would legitimately satisfy by adding informative channels. latent_tsne's docstring justifies its restriction for a shared 2D embedding, where a common feature space is a hard requirement; it does not state a project-wide rule. Choosing between matched-4ch, all-channels, or reporting both (plus a per-branch n_features column) is a spec judgment a person must make — README is silent on classify's feature set, so 'fixing the code' either way just relocates the mismatch.

## eo_ec_pipeline/band_power_check.py:25 — Relative band-power computation duplicated in two modules and already diverged  _(lens: maintainability, round 1)_

The factual core of the finding checks out against the code and is not merely stylistic. band_power_check.py:25-31 + 35-44 and analyze_session.py:82-89 are genuinely two copies of the same integrate-each-band-then-divide-by-total computation, and they have diverged in two places: gamma is (30.0, 45.0) vs (30, 50), and the PSD window is fmin=1.0/fmax=45.0 vs fmin=1.0/fmax=60. That divergence is numerically consequential, not cosmetic (see repro), so an operator running both tools on the same session does get different 'relative power' numbers. What blocks a 'confirmed' verdict is that the fix is not mechanical -- it forces two judgment calls a person must make. (1) Which gamma edge is authoritative? 45 Hz looks deliberate in band_power_check (it stops short of the 50 Hz mains region), while analyze_session's fmax=60 is load-bearing for a second purpose: the very same Spectrum object is handed to spectrum.plot() at analyze_session.py:99 for visual diagnostics, where seeing the mains ridge above 45 Hz is useful. Unifying fmax to 45 would silently degrade that plot; unifying to 60 would import mains energy into band_power_check's gamma. Either direction relocates the mismatch rather than resolving it. (2) Where would the shared helper live? The finding cites analyze_session.py:24-25's sys.path insert as precedent, but that insert reaches analyze_session's OWN parent (ingestion/) -- it is a within-tree import. A shared band-power helper would have to couple eo_ec_pipeline/ to ingestion/, two sibling top-level trees that are currently independent, which is an architectural decision, not a refactor. I did partially refute the sharpest sub-claim: the docstring at band_power_check.py:48-51 says 'same convention as ingestion/src/analyze_session.py' in a sentence whose subject is the normalization scheme ('each band's integrated power as a fraction of the total ... instead of raw log power'). Under that reading the cross-reference is still true -- both files do integrate-then-normalize -- so it is misleading about band edges rather than flatly false. Also checked and found no third copy: eo_ec_pipeline/features.py is alpha-band only (features.py:34) and defines no BANDS table, so the duplication is exactly 2x and ~10 lines, which is small enough that a human may reasonably prefer to just reconcile the constants and tighten the docstring over introducing a cross-tree shared module.

## ingestion/src/record_eeg.py:46 — Recording binds to any LSL "EEG" outlet with no identity check  _(lens: security, round 2)_

The code claim checks out exactly: record_eeg.py:42-46 calls resolve_byprop('type','EEG',timeout=30) and binds StreamInlet(streams[0]) with no test of name(), source_id(), or hostname, and the same unfiltered streams[0] pattern is in contact_watch.py:30, print_eeg.py:40, plot_live.py:31. pylsl's resolve_byprop returns as soon as minimum=1 outlet answers, and resolution is a UDP multicast/broadcast query answered LAN-wide by default, so whichever type=EEG outlet replies first wins; the CSV is then named from --user regardless and nothing downstream re-checks provenance. The contrast with the sibling is real too: muse_supervisor._confirm_stream_when_live (ingestion/src/muse_supervisor.py:117) explicitly matches `address in s.source_id()` and its docstring states that matching the connected address is the only unspoofable check. What makes this a human call rather than a mechanical fix is that record_eeg.py has no notion of which headset it should be recording — it is a standalone script whose documented precondition is just 'run src/stream_eeg.py in another terminal', and it is not even the README's canonical acquisition path (the data-collection checklist specifies Mind Monitor CSV export -> muse_to_fif.py). Any fix has to pick a policy: a new --stream-name/--source-id/--address argument (changing the operator workflow and the supervisor handoff), or abort when more than one EEG outlet resolves (which does not actually authenticate anything and is unreliable since resolution returns at the first responder), or configure LSL to localhost-only via lsl_api.cfg (no such config exists in the repo, and it is an environment change, not a code change). Choosing among those, and deciding whether the ambient-LAN threat matters for a 4-subject single-operator lab session, is a design decision.
